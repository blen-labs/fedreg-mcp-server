# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## What this is

`@blen/fedreg-mcp-server` — a "code-mode" MCP server for three U.S. government APIs: Federal Register (`fr.*`), eCFR (`ecfr.*`), and regulations.gov (`regs.*`). Instead of dozens of narrow tools it exposes exactly three — `search_api`, `describe_schema`, `execute` — and lets the model write JavaScript that runs in a locked-down sandbox with one global per source. Transports: stdio (default) and Streamable HTTP (`--http`).

## Commands

Run everything from this directory (`pnpm@12.21.0` pinned via `packageManager`; Node `^24.11.0 || ^26.0.0`):

```bash
pnpm install --frozen-lockfile
pnpm audit --audit-level moderate       # CI gate; the lockfile must have no moderate+ advisories
pnpm typecheck                          # tsc --noEmit (src + test), web/ and web/e2e — THE correctness gate (TypeScript 6 via `@typescript/typescript6`)
pnpm test                               # vitest run (all test/*.spec.ts, ~1s, no network/keys needed)
pnpm test test/search.spec.ts           # single file (args forward to vitest, no -- needed)
pnpm test test/search.spec.ts -t "bm25" # single test by name (pair with file path to keep it fast)
pnpm lint                               # eslint . — typescript-eslint recommended + type-aware promise rules in src/ (floating/misused promises, no console except stderr), react-hooks in web/, plus core rules kept from the old Biome setup (no-template-curly-in-string, default-case-last, array-callback-return, no-self-compare, radix, no-constructor-return)
pnpm test:web                           # build web, then Playwright + axe (web/e2e); journey.spec.ts needs TEST_DATABASE_URL + Deno
pnpm kit:check                          # shared portal kit vs web/portal-kit.json (test/portal-kit.spec.ts runs it too)
pnpm docs:check                         # every code fence in README, CONTRIBUTING, docs/, deploy/ and the site pages names a language (test/docs-source.spec.ts runs it too, and runs every shell block with stub commands)
pnpm build                              # tsc -p tsconfig.build.json && pnpm build:web (Vite → dist/web) && chmod
pnpm dev                                # tsx src/bin.ts (stdio)
pnpm dev --http                         # HTTP transport; also --port, --host, --sandbox, --insecure
pnpm dev --rotate-keys                  # account mode only: re-encrypt stored keys under ENCRYPTION_ACTIVE_KEY_ID, then exit (not combinable with --http/--insecure/--port)
```

- In `pnpm build`, the `|| true` guards only the `chmod` — a `tsc` failure DOES fail the build. `pnpm typecheck` remains the broader gate (it also covers `test/**`, which the build config excludes).
- CI (`.github/workflows/ci.yml`) runs `typecheck`, `lint`, `build`, `test` in that order (build first: the Postgres-gated account frontend test serves `dist/web` and skips without it) on Node 24 and 26 against a Postgres 17 service (preceded by `pnpm audit`), an `accessibility` job (Postgres + Deno + Chromium: `pnpm test:web`), plus an npm-package/MCPB job (pack contents, bundle prepare/pack, `scripts/mcpb-smoke.mjs` on Node 26 and 24), a Docker job (refuses to start without auth; `execute` returns 42 in the Deno sandbox over a 2026-07-28 request) and a conventional-commits job. The test gates must pass; the PR template also requires them as checkboxes.
- A green `pnpm test` on a machine with NO sandbox runner does not prove the sandbox works: sandbox-execution tests are gated on `await runner.available()` and report a skip when their runner is unavailable. CI installs isolated-vm AND Deno and sets `FEDREG_REQUIRE_RUNNERS=1`, under which `test/required-runners.spec.ts` fails if isolated-vm, Deno or `TEST_DATABASE_URL` is missing, so a green CI run means those tests ran. Set it locally to get the same guarantee.

## Architecture

Request flow (both transports converge on the same tool catalog):

```text
stdio | Streamable HTTP (+OAuth, per-IP bucket, quotas)     src/server/{stdio,http}.ts
  -> buildMcpServer (SDK v2 McpServer, 3 registerTool calls) src/server/mcpServer.ts, toolCatalog.ts
  -> tools: searchApi | describeSchema | execute             src/tools/
  -> execute: AST preflight -> sandbox runner                src/sandbox/{policy,isolate,deno}.ts
  -> sandbox globals (fr/ecfr/regs Proxies) --RPC bridge--> dispatch()   src/sdk/runtime.ts
  -> per-source HttpClient (undici + LRU + retry)            src/util/httpClient.ts
  -> upstream government APIs
```

`buildSupervisor(cfg)` in `src/supervisor/index.ts` is the single composition root: it assembles sources, SDK bindings, corpus, sandbox, and quota objects into `CatalogDeps`, which everything downstream receives by injection. All env vars are read in `src/bin.ts` (plus `FEDREG_LOG_LEVEL` in the logger) — nothing else touches `process.env`, and there is no dotenv: `.env.example` is documentation only.

**Source registry** (`src/sdk/sources/`): each source is a factory returning `{ name, label, enabled, disabledReason?, client, methods, corpus }`. The frozen `methods` table explicitly registers public SDK methods; dispatch never traverses `client` or its internals. Adding a source = one factory + one line in `getSources()` + a `schema/<name>.json` corpus file — tools, sandbox injection, and dispatch are registry-driven. Source names are validated at boot as safe JS identifiers (they get string-interpolated into generated sandbox code — the validation is the security precondition). Disabled sources (e.g. `regs` without `FEDREG_REGS_API_KEY`) are still registered: the sandbox global exists and corpus stays searchable, but dispatch returns `SourceUnavailable` instead of a `ReferenceError`. This is by design and tested — don't "fix" it.

**Corpus** (`schema/{fr,ecfr,regs}.json`): hand-written, NOT generated. `search_api`/`describe_schema` only surface what's in these files, so every new SDK method needs a matching corpus entry (PR-template checkbox). Loaded at runtime via `readFileSync(resolve(__dirname, '../../../schema/...'))` from the compiled location — `schema/` must ship as a sibling of `dist/`, and moving `src/sdk/sources/` breaks the path.

**Sandbox**: two layers — an acorn AST preflight (`src/sandbox/policy.ts`, bans imports/eval/`process`/`globalThis`/`constructor`/`__proto__`/etc.) and then either `isolated-vm` (fresh V8 isolate, heap cap + timeout) or a `deno run --no-prompt` subprocess (no `--allow-*` flags; a fixed supervisor runs user code in a permissionless Worker and talks to the host in token-prefixed JSON lines; `memoryMb` maps to V8's old-space limit). The host owns the deadline on both runners and nothing user code sends can cancel it; byte budgets live in `src/sandbox/limits.ts` and results are JSON round-tripped (`undefined` → `null`). User code is wrapped in `(async () => { ... })()`, so top-level `await`/`return` are legal. The preflight parses plain JavaScript — TypeScript syntax is a `PolicyError`, and nothing strips types; `test/examples.spec.ts` keeps `examples/*.js` pasteable. With no usable runner the server still starts and `execute` returns `SandboxUnavailable`; with `processIsolation` (authenticated HTTP) `pickSandbox` throws for `--sandbox isolate` and otherwise only ever returns Deno. The Deno runner (ported from uspto-mcp-server) runs code as a module in a Worker that deletes every non-language global, with V8 code generation from strings disabled, an RSS watchdog, and bounded frames.

**HTTP transport** (`src/server/http.ts`): MCP `2026-07-28` — stateless, no `initialize` handshake, no `Mcp-Session-Id`. `createMcpHandler` builds a fresh `McpServer` + tool catalog **per request** via a factory, so the subject a tool sees always comes from that request's own bearer token; auth runs on every request. Pre-2026 clients are served by the SDK's stateless legacy fallback (`legacy: 'stateless'`), and `GET`/`DELETE /mcp` return 405. It fails closed: `--http` without `--insecure` refuses to start unless an OIDC provider (`generic-oidc`/`clerk`/`workos`/`auth0`) or `accounts` is configured; unknown providers stop startup; OIDC requires issuer + audience + JWKS (https, or http on loopback), asymmetric algorithms, `exp`/`sub`, and every `FEDREG_AUTH_SCOPES` scope (403 `insufficient_scope`). Trusted Host values come from `FEDREG_PUBLIC_ORIGIN`/`FEDREG_ALLOWED_HOSTS` plus loopback on the listening port; binding non-loopback without either is a startup error. `--insecure` defaults the bind address to 127.0.0.1. Authenticated HTTP (incl. accounts) sets `processIsolation`: only the Deno runner is allowed (`pickSandbox`). stdio has no auth and no subject, so per-subject quotas are skipped there. In account mode (`src/accounts/app.ts`) the anonymous `/mcp` validates `Origin` (`originAllowed`; 403 `origin_not_allowed`; `FEDREG_ALLOWED_ORIGINS` extends it; clients that send no Origin pass). `/mcp/account` accepts any Origin because hosted connectors send theirs (see Known traps), and the OAuth/discovery endpoints keep `Access-Control-Allow-Origin: *`.

**Bearer admission in account mode** (`src/accounts/token-admission.ts`, `digest-gate.ts`, docs/accounts.md): tokens this server issues are `at1.<kid>.<iat>.<random>.<MAC>` (MAC keyed from `BETTER_AUTH_SECRET`, info `fedreg-access-token-mac/<kid>`); `/mcp/account` refuses bad shape/MAC/age with no database work, remembers rejections (fixed 60 s) and serialises lookups per digest, and keeps the old failed-token budget only for legacy-shaped tokens (release 1; release 2 deletes that branch, no sooner than 15 min + 60 s after release 1 is fully deployed). Changing `accessTokenExpiresIn` needs the larger lifetime in the bound until old tokens expire. The OIDC verifier (`src/server/authz.ts`) and the anonymous `/mcp` never see these checks.

**Concurrency and cancellation** (`src/tools/execute.ts`): `ExecutionLimiter` (global 8 / per-subject 2 by default, `FEDREG_MAX_CONCURRENT_EXECUTIONS` / `FEDREG_MAX_EXECUTIONS_PER_SUBJECT`, defaults in `EXECUTION_DEFAULTS`) fails fast with a `Busy` result over the cap; it travels in `CatalogDeps` so `/mcp` and `/mcp/account` share it. A result carrying the `TEARDOWN` promise (Deno process not yet exited) keeps its slot until it settles. Each execution has an `AbortController` combining `ctx.mcpReq.signal` (client cancel/disconnect), `shutdownSignal` (aborted first in `bin.ts` shutdown) and the end of the execution; it goes to the runner and, via `runWithSignal`/`currentSignal` (`src/util/executionContext.ts`, AsyncLocalStorage), to `HttpClient`, whose gate waits, retry sleeps and requests all honor it. HttpClient/gate cancellation tests use a real loopback server because undici's `MockAgent` ignores aborts during a mocked delay.

**regulations.gov guardrails** (4 layers, all in-memory/single-process): per-execute call budget → per-subject hourly quota (any authenticated HTTP request — under `--insecure` every client collapses to subject `anonymous` and shares one bucket; stdio has no subject so it's skipped) → process-wide hourly token bucket (preflight, after the cache) → `retry429: false` so upstream 429s surface immediately. The API key lives host-side in a private `HttpClient` field and must never appear on `Source` objects, logs, or `JSON.stringify` output — tests assert this. A rate of `0` would mean "block everything", not "unlimited" — which is why `src/bin.ts` silently replaces any value < 1 with the default; disable regs by unsetting the key.

**Results and errors** (MCP SDK v2, verified on the wire):
- Tool results are compact JSON text plus the same object as `structuredContent`, validated against the tool's `outputSchema` (`OUTPUT_SCHEMAS` in `src/server/toolCatalog.ts`, converted once and cached in `mcpServer.ts`). The envelopes are unchanged: `{ hits, note }`, `{ found, entries?, message? }`, `{ ok, value?, logs, error?, durationMs }`.
- A failed `execute` (`ok: false`: thrown error, `PolicyError`, timeout, limit, `Busy`) returns `isError: true` WITH the full envelope `{ ok, error: { name, message, status? }, logs, durationMs }` (`isFailure` on the catalog descriptor).
- `isError: true` also appears for a thrown handler exception (e.g. Zod parse failures) **and for argument-validation failures**: `registerTool` attaches the SDK's Ajv validator, and `zodToJsonSchema` emits `additionalProperties: false`, so an unknown argument key yields `isError` + `"Input validation error: … must NOT have additional properties"`.
- An **unknown tool name is no longer a tool result at all** — the v2 `tools/call` path throws before the handler's try/catch, so it surfaces as a JSON-RPC error `{"error":{"code":-32602,"message":"Tool X not found"}}` (HTTP 200, no `result`). Clients that read `result.isError` to detect a bad tool name see `undefined`.

## Hard project rules (from CONTRIBUTING / SECURITY / the PR template, plus code conventions)

- **Never commit or push directly to `main`.** Every change lands via a feature branch + PR — `main` is release-bearing (every merge auto-releases), and the only direct writer is the release workflow's own `chore(release)` commit.

- **Anything that weakens the sandbox is out of scope** — never add `fetch`, `import`, filesystem, env, or subprocess access to the sandbox surface. Sandbox-escape reports go to a private GitHub Security Advisory, never a public issue.
- The public API (three tools; `fr.*`/`ecfr.*`/`regs.*` globals) is stable; breaking it needs a major version bump and migration note.
- PR checklist beyond the four gates: HTTP-visible change → add a case to `test/http-integration.spec.ts`; sandbox-visible change → add a positive AND a negative case to `test/sandbox.spec.ts`; new SDK method → corpus entry in the owning `schema/*.json`, a `methods`-table registration in its source factory, and a row in `test/dispatch.spec.ts`.
- ESM everywhere: relative imports use the `.js` extension even in `.ts` sources.
- Logs go to stderr only (`src/util/logger.ts`) — stdout is reserved for stdio JSON-RPC; a stray `console.log` in server code corrupts the protocol stream.

## Test conventions

- HTTP mocking is undici `MockAgent` injected via the `dispatcher` config field on `HttpClient`/`SourceConfig` — never `nock`, never `setGlobalDispatcher`. A new client that doesn't thread `dispatcher` through will silently make real network calls in tests.
- No `vi.mock`/`vi.fn`/fake timers anywhere; the pattern is hand-written fakes satisfying the DI interfaces (`SandboxRunner`, `RpcBridge`, `preflightLimiter`). Follow it.
- No vitest globals and no setup files — every spec imports `describe/it/expect` from `vitest` explicitly. `pool: 'forks'` is required (sandbox runners spawn processes).
- `test/http-integration.spec.ts` is the canonical end-to-end check, and covers both eras: stateless `2026-07-28` requests (with the `_meta` envelope and `Mcp-Method`/`Mcp-Name` headers) and the legacy `initialize` fallback. Its `rpc()` helper builds the modern shape; use `post()` for raw/legacy bodies.
- `test/official-client.spec.ts` drives the server with the real `@modelcontextprotocol/client` SDK, which builds the `_meta` envelope and routing headers itself. Hand-built requests can't catch a protocol misunderstanding — the same wrong assumption goes into both the test and the server — so keep this spec passing when touching the transport. It also asserts `structuredContent` and `outputSchema` conformance: the client validates each result against the schema it listed, so a result that drifts from `OUTPUT_SCHEMAS` makes `callTool` throw.
- **MCP Inspector 2.1.0 cannot exercise the 2026-07-28 path.** Its CLI exposes no version-negotiation flag and the v2 client defaults to `versionNegotiation: 'legacy'`, so `npx @modelcontextprotocol/inspector --cli` always drives the *legacy* leg (verified on the wire: it sends `initialize`). It's a good compat-leg check; for the modern path use the client SDK directly with `versionNegotiation: { mode: 'auto' }` or `versionNegotiation: { mode: { pin: '2026-07-28' } }` — note the pin is a **nested object**, not `{ mode: 'pin', pin: ... }`; the flat form is not a valid `VersionNegotiationMode` and silently degrades to legacy negotiation.
- Several specs match URL-encoded query fragments (`conditions%5Bterm%5D=...`); changing query serialization surfaces as cryptic MockAgent "no interceptor" errors, not assertion diffs.

## Known traps

- **Don't add an Origin allowlist to the signed-in MCP endpoint (`/mcp/account`).** Hosted connectors (claude.ai, chatgpt.com) send their own `Origin` there; every request carries a bearer token (never a cookie) and the Host check already blocks DNS rebinding. Only the anonymous `/mcp` (no token to check) refuses foreign Origins (`FEDREG_ALLOWED_ORIGINS` extends it). A test pins both.
- `LATEST_PROTOCOL_VERSION` / `SUPPORTED_PROTOCOL_VERSIONS` exported by the v2 SDK are the **legacy-era** vocabulary (`2025-11-25` and older) kept for the backward-compat leg — they are NOT the revision this server speaks, and reading them as an era signal is the documented way to wrongly conclude v2 lacks 2026-07-28 support (upstream PR #2585). The modern value lives in the SDK's `core-internal` as `FIRST_MODERN_PROTOCOL_VERSION` but is not exported, so use `MCP_PROTOCOL_VERSION` from `src/server/mcpServer.ts`; a test pins `/health` to it.

- Execute limits (`timeoutMs`, `memoryMb`) are per-call Zod defaults on the `execute` tool in `src/tools/execute.ts` — they are NOT env-configurable; don't invent `FEDREG_EXEC_*` vars (concurrency caps are the exception: `FEDREG_MAX_CONCURRENT_EXECUTIONS` / `FEDREG_MAX_EXECUTIONS_PER_SUBJECT`). Transport is chosen only by the `--http` flag, never by env.
- MCPB packaging: `pnpm build && pnpm mcpb:prepare && pnpm mcpb:pack` produces `fedreg-mcp-server.mcpb` (manifest is built by `buildManifest()` in `scripts/mcpb-prepare.mjs` and schema-validated during prepare). The prepare step copies `pnpm-lock.yaml`, `pnpm-workspace.yaml` and `.pnpmfile.cjs` into `mcpb-build/` so it is its own workspace root, then runs `pnpm install --prod --frozen-lockfile --ignore-scripts --config.node-linker=hoisted` (hoisted is required: symlinked layouts don't survive zipping; do not reintroduce `--ignore-workspace`/`--no-lockfile`). isolated-vm 7 loads its shipped prebuilt binary without install scripts on Node 24/26; elsewhere `execute` needs Deno on the host or reports `SandboxUnavailable`. The optional `regs_api_key` user_config becomes `FEDREG_REGS_API_KEY`.
- `dist/web/THIRD_PARTY_NOTICES.txt` is emitted by the Vite plugin in `web/third-party-notices.ts` (Rollup `emitFile`, not a file write — the output dir doesn't exist yet in `generateBundle`); the CI package job requires it in the npm pack. `web/vite.config.ts` imports it with a `.ts` extension, hence `allowImportingTsExtensions` in `web/tsconfig.json`.
- `dist/` is never cleaned between builds — delete it manually after renaming/moving source files. Never edit `dist/` or `mcpb-build/` (both are gitignored build artifacts; `mcpb-build/` is only produced locally by `pnpm mcpb:prepare`, which wipes and regenerates it).
- `buildSupervisor` instantiates the sources twice (once directly, once inside `buildSdk`), so HttpClients/LRU caches exist in duplicate; the corpus comes from the first set, dispatch uses the second. Know this before refactoring wiring or reasoning about cache memory.
- Version strings live in three places (package.json, `src/server/mcpServer.ts`, `src/sdk/bindings.ts` `version()`). Releases are continuous but gated: a push to main runs the full CI workflow, then `.github/workflows/release.yml` (gates → cut → publish). `scripts/release.mjs` first asks `releaseReason` (`scripts/release-lib.mjs`) whether the commits since the last tag can change what users install (feat/fix/perf/breaking, or any commit touching `SHIPPED_PATHS`, a shipped `package.json` field, or the lockfile's production tree — plus the portal's `BUNDLED_DEV_DEPENDENCIES` (react, radix-ui, vite, tailwind … are devDependencies compiled into `dist/web`, so their `package.json` entries and lockfile subtree count; a test fails when `web/` imports a package missing from that list)); build/chore/ci/docs/test-only ranges release nothing and ship with the next release (or via a `force` dispatch). Otherwise it bumps all three version places (the two source lines carry `x-release-version` markers — don't remove them), writes the CHANGELOG section, and the `cut` job builds the tarball and MCPB bundle, pushes the `chore(release)` commit and tag atomically as the release GitHub App, and attaches both to the GitHub Release; `publish` (OIDC, provenance) uploads that exact tarball. Commit types set the bump (breaking → major, `feat` → minor, anything else → patch); never hand-edit versions or tags. If you add a shipped top-level path, add it to `SHIPPED_PATHS`. See CONTRIBUTING "Releasing".

## Portal (web/) and accessibility

- `web/src/components/kit/` (Page, SiteHeader, SiteFooter, Shell, Landing, Notice, Field, CopyField, error pages), `components/ui/`, `index.css`, `lib/utils.ts` and the BLEN logo are a **kit shared byte for byte** with BLEN's other MCP servers (the reference copy is `uspto-mcp-server`), hashed in `web/portal-kit.json` (`pnpm kit:check`; `test/portal-kit.spec.ts` runs it too). Don't edit kit files here and don't run `kit:update` to hide drift: change them in the reference and copy them over. Product text lives in `web/src/brand.tsx`; product pages (`pages/*`), `components/fields.tsx`, `lib/api.ts` and `lib/auth.ts` stay per repo. Don't put product strings in kit files.
- Target WCAG 2.2 AA / Section 508 (`docs/accessibility.md`). Each page renders through `Page`/`Shell` (skip link, header/main/footer landmarks, one h1, tab title). Pages navigate with full loads, not client-side routing. Errors use `Notice` (role=alert), confirmations `Notice kind="success"` (role=status). Field errors go through `Field`'s `error` (aria-invalid + aria-describedby). Busy buttons use `aria-disabled` plus a guard, not `disabled`, so focus is not dropped. Tokens keep text >= 4.5:1 and borders/focus ring >= 3:1 — `web/e2e/accessibility.spec.ts` (axe, light/dark, 1280/320 px) fails on regressions.
- The policy pages (`/privacy-policy`, `/terms`) are the connectors' registered privacy policy, so their text is in the HTML: `web/prerender.ts` (shared, like `third-party-notices.ts`, not in the kit manifest) builds `web/src/prerender.tsx` with `build.ssr` after the client build, renders `Policy` with `renderToString` and writes `dist/web/privacy-policy.html` and `terms.html` (index.html with the markup in `#root` and the title set). `main.tsx` hydrates a non-empty root and creates one otherwise, so keep the prerender entry in step with the client route. `PRERENDERED_ROUTES` in `src/accounts/app.ts` serves them with the portal CSP. `web/e2e/prerender.spec.ts` and the `node:http` test in `test/accounts.spec.ts` guard it.
- Server side: `PORTAL_ROUTES` in `src/accounts/app.ts` lists the SPA routes; Better Auth errors redirect to `/error` (`onAPIError.errorURL`); unknown paths answer browser navigations (`Sec-Fetch-Mode: navigate`, else `Accept: text/html`) with the portal's 404 and everything else with plain `Not found`; a 429 for a navigation is a small HTML page. Node's `fetch` always sends `sec-fetch-mode: cors`, so navigation tests use `node:http`.
- `web/e2e/fixtures.ts` mocks `/api/**` per state; `journey.spec.ts` runs `web/e2e/journey-server.ts` (the real app, Better Auth `testUtils` session, MockAgent for regulations.gov) on port 4175. `playwright.config.ts` keeps the journey's session cookies in a private `mkdtemp` directory (`JOURNEY_STATE`), written owner-only.
