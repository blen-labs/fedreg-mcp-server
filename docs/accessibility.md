# Accessibility

The portal (`web/`: home, sign-in, connect, consent, account, policies, error pages) targets
**WCAG 2.2 Level AA**. Section 508 of the
Rehabilitation Act incorporates **WCAG 2.0 Level AA** by reference; every 2.0 AA success
criterion is also a 2.2 AA criterion, except 4.1.1 Parsing, which WCAG 2.2 removed as obsolete
and which Section 508 still lists. The portal is generated by React, which
emits well-formed markup (4.1.1 is met in practice; axe's markup rules cover duplicate ids).

The MCP tools themselves have no user interface: an AI assistant calls them.

## What is tested automatically

`pnpm test:web` (CI job "accessibility") runs Playwright with axe-core in Chromium:

| Check | Where | Criteria |
|---|---|---|
| axe rules tagged `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`, plus `best-practice` | every portal page and state (signed out, signed in, key saved or not, errors, consent warning, 404), in light and dark color schemes, at 1280 and 320 CSS px | many, incl. 1.1.1, 1.3.1, 1.4.3, 2.4.2, 2.5.3, 4.1.2 |
| No horizontal scrolling at 320 CSS px | every portal page | 1.4.10 Reflow |
| Increased line, letter, word and paragraph spacing does not clip or overflow | every portal page | 1.4.12 Text Spacing |
| One `h1`, one banner, main and contentinfo landmark, a page title | every portal page | 1.3.1, 2.4.2, 2.4.6 |
| The first Tab reaches "Skip to main content", which moves focus to the main content | every portal page | 2.4.1 Bypass Blocks |
| A failed key save sets `aria-invalid` and describes the field with the error | account page | 3.3.1, 3.3.3 |
| A confirmation is a polite status message and receives focus | account page | 4.1.3, 2.4.3 |
| Copying a URL is announced | home page | 4.1.3 |
| The real signed-in journey (save a regulations.gov key, connect and consent, run `execute`, sign out), axe-checked on each live page | `web/e2e/journey.spec.ts` against a real server, PostgreSQL and Deno | as above |

Design tokens (`web/src/index.css`) are chosen for contrast: body and muted text at least 4.5:1
on every surface they sit on; field borders, radio borders and the focus ring at least 3:1
against their background (1.4.3, 1.4.11). Motion is disabled under `prefers-reduced-motion`.

## Manual checks

Automated tools find only part of the problems. Before a release that changes the portal, check these by hand and record the result in the pull request:

- **Keyboard only** (2.1.1, 2.1.2, 2.4.3, 2.4.7, 2.4.11): every page can be used with Tab,
  Shift+Tab, Enter and Space; focus order follows the page; the focus indicator is always visible
  and never hidden behind other content; no keyboard trap.
- **Screen reader** (1.3.1, 2.4.6, 4.1.2, 4.1.3): VoiceOver (macOS Safari) and NVDA (Windows
  Firefox or Chrome): headings and landmarks list correctly; form fields announce label, help and
  errors; "Copied", "Key saved" and sign-out errors are announced; the consent page reads in order.
- **Zoom** (1.4.4, 1.4.10): browser zoom to 200% and 400% at 1280 px wide: no lost content or
  function, no horizontal scrolling at 400%.
- **Accessible authentication** (3.3.8): sign-in is "Continue with Google"; no cognitive test is
  added by this site. The key field allows paste and password managers.
- **Target size** (2.5.8): interactive targets are at least 24 by 24 CSS px or spaced so.
- **Consistency** (3.2.3, 3.2.4, 3.2.6): the header, footer and help links are in the same place
  and order on every portal page.

Last full manual pass: not yet recorded. Keyboard, reflow and text-spacing behaviour is covered
by the automated suite above; the screen-reader and browser-zoom passes are outstanding.

## Reporting a problem

Open an issue with the page, what you tried, your browser and assistive technology. Problems that
block access are treated as bugs.
